## ADR-007: PostgreSQL + Neon Serverless + Drizzle ORM
- **Status:** Accepted (Phase 3.2)
- **Supersedes:** ADR-001 (SQLite + WAL)
- **Context:** The Termux ARM64 environment cannot reliably run native SQLite bindings through Prisma (requires platform-specific binary compilation). Additionally, ArcadeVerse targets a production deployment on serverless/edge infrastructure where a managed PostgreSQL service (Neon) provides connection pooling, branching, and zero cold-start HTTP connectivity without native binaries.
- **Decision:**
  - Replace SQLite with **PostgreSQL** hosted on **Neon** (serverless, HTTP-compatible).
  - Replace Prisma ORM with **Drizzle ORM** (`drizzle-orm` + `drizzle-kit`).
  - Use **`@neondatabase/serverless`** WebSocket/HTTP driver — zero native binaries, ARM64 safe.
  - Schema source of truth: `src/lib/db/schema/index.ts`.
  - Migration artefacts: `drizzle/migrations/` (generated by `drizzle-kit generate`).
  - Drizzle Kit config: `drizzle.config.ts` (project root).
  - Connection string injected via `DATABASE_URL` environment variable — no credentials committed to the repository.
- **Consequences:**
  - Zero native binary compilation required on Termux ARM64.
  - Drizzle ORM provides type-safe SQL query builder aligned with PostgreSQL semantics.
  - Neon serverless driver supports Next.js Route Handlers and Edge Runtime without connection pool exhaustion.
  - All existing architectural decisions (ADR-002 through ADR-006) — dual-currency ledger, idempotency, config versioning, anti-cheat, prize pre-modeling, bilingual modeling — are **unchanged**; only the engine and ORM layer changes.
  - The `prisma/schema.prisma` file (untracked, Phase 3.1 reference artefact) is **retained as documentation only** and will not be used at runtime.

## ADR-002: Dual-Currency Append-Only Ledger Architecture
- **Status:** Accepted (Phase 3.1)
- **Context:** Online arcade games are prone to race conditions, balance tampering, and duplicate rewards on network hiccups.
- **Decision:**
  - Never maintain mutable `user.coins` or `user.tickets` fields as the source of truth.
  - Record all financial mutations in `coin_ledger` and `ticket_ledger` as signed integers (`+` for credits, `-` for debits).
  - Enforce a unique `idempotencyKey` on every ledger entry.
  - Maintain a cached `UserWallet` snapshot table synchronized within the same ACID transaction for microsecond O(1) balance queries.
- **Consequences:**
  - Complete historical auditability of every coin spent and ticket won.
  - Mobile retry requests with the same idempotency key are safely discarded without double-charging or double-granting.

## ADR-003: Immutable Configuration Versioning and Session Pinning
- **Status:** Accepted (Phase 3.1)
- **Context:** Section 1 of `ARCADEVERSE_GAME_SYSTEM_LOCK.md` dictates: *"A session retains the configuration version selected at its start. New published configurations apply to new sessions. Never silently alter an active session's rules."*
- **Decision:**
  - `GameConfiguration` versions are monotonically increasing per game.
  - State machine: `draft` -> `validating` -> `testing` -> `approved` -> `published` -> `rolled_back`.
  - Once marked `published`, a configuration cannot be edited. Edits require creating a new version draft.
  - Every `GameSession` stores a non-nullable foreign key `configVersionId` referencing the exact configuration version active at start.
- **Consequences:**
  - Guarantees replay integrity and post-game score auditing.
  - Prevents race conditions when an admin publishes new parameters while thousands of active games are running.

## ADR-004: Anti-Cheat Score Event Tracking
- **Status:** Accepted (Phase 3.1)
- **Context:** Client game engines (e.g. Phaser) run in untrusted browser environments. Client-calculated final scores cannot be trusted.
- **Decision:**
  - Individual score events during gameplay are recorded in `Score` with `clientRef` deduplication.
  - The server verifies session duration (`durationMs`), scoring rate bounds, and target lifetimes against the pinned `GameConfiguration` before issuing rewards.
  - If score violates statistical or physical limits configured for that version, the session is marked `abandoned` or flagged.
- **Consequences:**
  - Memory-hackers and automated script injectors cannot arbitrarily mint tickets.

## ADR-005: Pre-Modeling Prize Redemption Domain (Phase 4 Continuity)
- **Status:** Accepted (Phase 3.1)
- **Context:** The Phase 2 UI displays the "Prize Redemption Catalog" tab targeting Phase 4. If prizes and orders are not modeled now, ticket deductions in Phase 3 would lack proper foreign key references.
- **Decision:** Model `Prize` and `RedemptionOrder` in Phase 3.1, linking `TicketLedger.redemptionId` with `onDelete: SetNull`.
- **Consequences:**
  - Zero breaking database migrations when transitioning from Phase 3 to Phase 4.
  - Complete end-to-end schema integrity from day one.

## ADR-006: Bilingual Domain Modeling (EN & MY)
- **Status:** Accepted (Phase 3.1)
- **Context:** ArcadeVerse requires complete bilingual support for Myanmar (`my`) and English (`en`).
- **Decision:**
  - User-facing catalog entities (`Game`, `Prize`, `DailyChallenge`, `Achievement`) include dedicated columns for both English (`title`, `description`) and Myanmar (`titleMy`, `descriptionMy`).
  - User preference stores the active locale (`language: "my" | "en"`).
- **Consequences:**
  - Eliminates external translation key lookups for dynamic content.
  - Enables admin operators to curate localized copy directly in the Admin Studio.
